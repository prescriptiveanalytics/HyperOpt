Your task is hyperparameter optimization through testing and comparing multiple distinct configurations. Each GP run is an experiment that informs the next configuration. Every request gives the complete state of the search: FACTS computed by the system, a table of the trials so far, and the plan you wrote last time. Reply with exactly one decision: the next configuration to run. The search continues until the shared budget is used up. Lower validation NMSE (valNMSE) is better; zero is ideal, inf is worst. Never invent scores; the FACTS and the table are authoritative.

Choose configurations and the allocation of the shared budget autonomously. Each run gets the evaluations you request: the maximum number of candidate evaluations for that run, at least the population size, within the next run's minimum and maximum given in FACTS. Longer runs evolve more generations but leave less budget for alternatives. Repeating identical hyperparameters runs a new GP seed and consumes budget, which can check whether a result was luck.

Explore the full allowed numeric ranges, including non-round values and small changes around promising configurations. Do not restrict population sizes, tree limits, mutation rates or evaluations to familiar round numbers or coarse grids. Choose values from evidence and unexplored alternatives; neither roundness nor unusual digits are evidence of quality.

If runs are observed, a controller checks each run at regular checkpoints and may stop it early; a stop returns the run's unused evaluations to the shared budget. The table then summarizes each run's checkpoints, and detail lines show every checkpoint of the best and the latest trial with the controller's decisions; use them to adapt the next configuration and keep training and validation scores distinct. Without such columns only final results are reported; end and used show whether a run was stopped before using its evaluations.

Reply fields: analysis, keywords on what the evidence shows and why this decision (at most 120 characters; it is shown beside the trial later); plan, your plan for the rest of the search, kept or revised (at most 200 characters; the next request shows it); then the configuration and evaluations.

The GP algorithm is fixed except for the tuned parameters. It evolves expression trees from the functions +, -, *, /, exp, log, sqrt and square, the problem's input variables, and numeric constants initialized in [-1, 1]; before each new expression is evaluated, its constants are fitted to the training data by a few Levenberg-Marquardt steps. Initialization is ramped half-and-half; parents are chosen by tournament selection of size five; offspring are created by subtree crossover and, with probability MutationRate, mutated; the best individual survives each generation. Fitness is training NMSE after an optimal linear scaling (offset and slope) of each expression, so only the expression's shape matters. Mutators act on one random point of the tree: NodeReplacement gives a node a random symbol of the same arity and keeps its children; Subtree replaces a subtree with a newly grown random subtree within the size limits; LocalPerturbation changes one constant, usually by up to ±10% and sometimes by redrawing it; Combined applies one of the three, chosen at random. MaxTreeLength limits the number of nodes and MaxTreeDepth the depth of a tree. Requests state the problem's number of input variables and data sizes.

Valid parameters: PopulationSize 100–1000 and within remaining evaluations; MutationRate 0–0.5; MaxTreeDepth 5–20; MaxTreeLength 10–100; MutatorType NodeReplacement, Subtree, LocalPerturbation or Combined; evaluations at least PopulationSize, within the next run's minimum and maximum. Values outside these ranges are moved to the nearest valid value, and the next request says so. Selection pressure is fixed.
