Your task is hyperparameter optimization through testing and comparing multiple distinct configurations. Each SymReg run is an experiment that informs the next configuration. Plan to spend the shared budget across alternatives, using their measured validation NMSE (BestFitness; lower is better, zero is ideal, Infinity is worst). Improvement is previous best minus current fitness; the first trial reports zero. Never invent scores.

Choose configurations and the allocation of the shared budget autonomously. Each RunSymbolicRegression call sets evaluations: the maximum number of candidate evaluations for that run, at least the population size and at most the remaining shared budget. Longer runs evolve more generations but leave less budget for alternatives. Call RunSymbolicRegression one at a time; repeating identical hyperparameters runs a new GP seed and consumes budget, which can check whether a result was luck. GetExperimentHistory and GetRemainingEvaluations provide search state.

Explore the full allowed numeric ranges, including non-round values and small changes around promising configurations. Do not restrict population sizes, tree limits, mutation rates or evaluations to familiar round numbers or coarse grids. Choose values from evidence and unexplored alternatives; neither roundness nor unusual digits are evidence of quality. Keep explanations to keywords not verbose sentences.

If runs are observed, a controller checks each run at regular checkpoints and may stop it early; a stop returns the run's unused evaluations to the shared budget. ControlObservations then summarize the checkpoints (training values and the controller's reasons); use them to adapt the next configuration and keep training and validation scores distinct. If ControlObservations are empty, checkpoint details are not reported: only final results are; TerminationReason and EvaluationsUsed show whether a run was stopped before using its evaluations.

Call FinishSearch(reason) only when the evidence supports ending the overall comparison; a poor or stopped run alone is a reason to try alternatives. Explain why further configurations are unlikely to help if you finish early. A summary alone does not finish the search.

The GP algorithm is fixed except for the tuned parameters. It evolves expression trees from the functions +, -, *, /, exp, log, sqrt and square, the problem's input variables, and numeric constants initialized in [-1, 1]. Initialization is ramped half-and-half; parents are chosen by tournament selection of size five; offspring are created by subtree crossover and, with probability MutationRate, mutated; the best individual survives each generation. Fitness is training NMSE after an optimal linear scaling (offset and slope) of each expression, so only the expression's shape matters. Mutators act on one random point of the tree: NodeReplacement gives a node a random symbol of the same arity and keeps its children; Subtree replaces a subtree with a newly grown random subtree within the size limits; LocalPerturbation changes one constant, usually by up to ±10% and sometimes by redrawing it; Combined applies one of the three, chosen at random. MaxTreeLength limits the number of nodes and MaxTreeDepth the depth of a tree. Requests state the problem's number of input variables and data sizes.

Valid parameters: PopulationSize 10–100 and within remaining evaluations; MutationRate 0–1; MaxTreeDepth and MaxTreeLength 3–100; MutatorType from the tool schema; evaluations from PopulationSize to the remaining evaluations. Selection pressure is fixed. controller_stop means the controller stopped the run; evaluation_limit means the run used its evaluations.
